## Repositorios y control de versiones

- **Repositorio**: almacén organizado y versionado de elementos del desarrollo. Tipos: de **código fuente** (Git, SVN), de **artefactos** binarios y paquetes (Nexus, Artifactory, Maven Central, npm, PyPI, NuGet; registros de contenedores como Docker Hub) y de **metadatos/modelos** (repositorio CASE).
- **Estructura típica de un proyecto**: `src/` (código), `test/` (pruebas), `docs/`, scripts de construcción (`pom.xml`, `build.gradle`, `package.json`), `README.md`, `LICENSE`, `CHANGELOG`, `CONTRIBUTING`, `.gitignore`. **Monorepo** (varios proyectos en un repositorio) frente a **multirepo**.
- **Control de versiones (VCS/SCM)**: registra los cambios, permite recuperar versiones anteriores, trabajar en paralelo, auditar autores y colaborar.
  - **Centralizado**: un único repositorio en el servidor (CVS, **Subversion/SVN**: números de revisión globales, `trunk/branches/tags`, `checkout/update/commit`).
  - **Distribuido**: cada desarrollador tiene una copia completa del historial (**Git**, Mercurial); permite trabajar sin conexión y ramas baratas.
- **Gestión de la configuración**: identifica elementos de configuración, controla los cambios, establece **líneas base** y audita el estado (interfaz GC de MÉTRICA v3).

### Git

- **Tres áreas**: **directorio de trabajo**, **área de preparación (*staging/index*)** y **repositorio** (`.git`). Flujo: `git add` (prepara) → `git commit` (confirma una instantánea con un identificador *hash* SHA-1 y un mensaje) → `git push` (publica).
- **Comandos clave**:

| Comando | Función |
|---|---|
| `git init` / `git clone` | Crear / copiar un repositorio |
| `git status`, `git diff`, `git log` | Consultar estado, cambios e historial |
| `git branch`, `git switch` / `checkout` | Crear y cambiar de rama |
| `git merge` | Integrar una rama en otra (*fast-forward* o fusión de tres vías; puede haber **conflictos**) |
| `git rebase` | Reaplicar commits sobre otra base (historial lineal; **no usar en ramas compartidas**) |
| `git fetch` | Descargar cambios remotos **sin integrarlos** |
| `git pull` | `fetch` + `merge` (o `rebase`) |
| `git push` | Enviar commits al remoto |
| `git stash` | Guardar temporalmente cambios sin confirmar |
| `git revert` | Crea un commit que **deshace** otro (seguro en ramas compartidas) |
| `git reset` | Mueve `HEAD` (`--soft`, `--mixed`, `--hard`; reescribe historial) |
| `git cherry-pick` | Aplica un commit concreto en otra rama |
| `git tag` | Marca versiones (`v1.2.0`) |
| `git blame`, `git bisect` | Autoría por línea; búsqueda binaria de un commit defectuoso |

- **`HEAD`** apunta al commit/rama actual; **`origin`** es el nombre habitual del remoto; **`.gitignore`** excluye ficheros del control de versiones.
- **Flujos de trabajo**: **Git Flow** (`main`, `develop`, `feature/*`, `release/*`, `hotfix/*`), **GitHub Flow** (ramas cortas + *pull request* a `main`), **trunk-based development** y *forking workflow*. **Pull/Merge Request**: propuesta de integración con **revisión de código**; ramas protegidas.
- **Versionado semántico (SemVer)**: `MAJOR.MINOR.PATCH` (cambios incompatibles / funcionalidad compatible / correcciones).
- **Plataformas de desarrollo colaborativo**: **GitHub**, **GitLab** (CI/CD integrada, autoalojable), **Bitbucket**, **Azure DevOps**, Gitea; gestión de *issues*, wikis, tableros y automatización (*Actions*, *pipelines*). En el sector público existe la forja del **Centro de Transferencia de Tecnología (CTT)** para compartir software de las Administraciones.

## Integración y entrega continuas (CI/CD)

- **Integración continua (CI)**: integrar los cambios con frecuencia en la rama principal, con **compilación y pruebas automáticas** en cada commit. **Entrega continua (*Continuous Delivery*)**: el software está siempre listo para desplegar, con **aprobación manual** hacia producción. **Despliegue continuo (*Continuous Deployment*)**: cada cambio que pasa las pruebas se despliega **automáticamente** a producción.
- Herramientas: **Jenkins**, GitLab CI, GitHub Actions, Azure Pipelines. **Contenedores** (Docker) y orquestación (Kubernetes), **infraestructura como código** (Terraform, Ansible). **Entornos**: desarrollo, pruebas/QA, **preproducción** y producción. Estrategias de despliegue: *blue/green*, *canary* y *rolling*. **DevOps**: cultura y prácticas que integran desarrollo y operaciones.
- **Gestión de dependencias y construcción**: Maven, Gradle, npm, pip, NuGet, Composer.

## Generación de código y de documentación

- **Generación de código**: **ingeniería dirigida por modelos (MDA/MDD**, estándar de la OMG): a partir de modelos (UML) se genera código; también generadores de código a partir de **OpenAPI**, *scaffolding* de frameworks, plantillas, ORM que generan entidades, **herramientas CASE** (L-CASE/U-CASE) y **lenguajes específicos de dominio (DSL)**. Los **asistentes de IA** aceleran la escritura, pero su código debe revisarse (seguridad, licencias, calidad).
- **Generación de documentación**: a partir de comentarios en el código: **Javadoc** (`/** … */` con `@param`, `@return`, `@throws`), **Doxygen**, **JSDoc**, Sphinx; documentación de APIs con **OpenAPI/Swagger**; *docs as code* (Markdown, MkDocs, Wiki). Tipos: documentación **de usuario**, **técnica/de diseño** y **de API**.

## Metodologías de desarrollo

### Modelos clásicos

| Modelo | Características |
|---|---|
| **Cascada (*waterfall*)** | Fases secuenciales (requisitos, análisis, diseño, implementación, pruebas, mantenimiento); poco flexible a cambios |
| **Modelo en V** | Cada fase de desarrollo tiene su fase de pruebas asociada (unitarias ↔ diseño detallado; integración ↔ diseño; sistema ↔ análisis; aceptación ↔ requisitos) |
| **Incremental / iterativo** | Se entrega por incrementos funcionales |
| **Espiral (Boehm)** | Iteraciones con **análisis de riesgos** en cada vuelta |
| **Prototipado, RAD** | Prototipos para aclarar requisitos; desarrollo rápido |
| **RUP / UP** | Iterativo e incremental, **dirigido por casos de uso**, centrado en la arquitectura; cuatro fases: **Inicio, Elaboración, Construcción y Transición** |

### Metodologías ágiles

- **Manifiesto Ágil (2001)**: valora **individuos e interacciones** sobre procesos y herramientas; **software funcionando** sobre documentación exhaustiva; **colaboración con el cliente** sobre negociación contractual; **respuesta ante el cambio** sobre seguir un plan. Doce principios.
- **Scrum**: marco de trabajo iterativo e incremental.
  - **Roles**: **Product Owner** (maximiza el valor, gestiona el *Product Backlog*), **Scrum Master** (facilita y elimina impedimentos) y **Developers** (equipo).
  - **Eventos**: **Sprint** (duración máxima de **un mes**), *Sprint Planning*, ***Daily Scrum*** (**15 minutos**), *Sprint Review* y *Sprint Retrospective*.
  - **Artefactos**: *Product Backlog*, *Sprint Backlog* e *Incremento*, con compromisos: *Product Goal*, *Sprint Goal* y **Definición de Hecho (*Definition of Done*)**.
- **Kanban**: tablero visual (por hacer / en curso / hecho), **límites de trabajo en curso (WIP)** y flujo continuo, sin iteraciones fijas.
- **XP (Extreme Programming)**: programación en parejas, **TDD**, integración continua, refactorización, entregas pequeñas, propiedad colectiva del código.
- **Historias de usuario**: «Como *<rol>* quiero *<funcionalidad>* para *<beneficio>*», con **criterios de aceptación**; estimación en **puntos de historia**; **velocidad** y **gráfico *burn-down***.
- **Lean**, **SAFe** (escalado ágil), **DevOps**.

### Metodologías y normas en las Administraciones y la industria

- **MÉTRICA v3**: metodología de la Administración española para la planificación, desarrollo y mantenimiento de sistemas de información. **Procesos principales**: **PSI** (Planificación de Sistemas de Información), **DSI** (Desarrollo de Sistemas de Información) y **MSI** (Mantenimiento). El desarrollo se descompone en **EVS** (estudio de viabilidad), **ASI** (análisis), **DSI** (diseño), **CSI** (construcción) e **IAS** (implantación y aceptación). **Interfaces**: gestión de proyectos, seguridad, aseguramiento de la calidad y gestión de la configuración. Ojo: la sigla **DSI** se usa tanto para el proceso de *Desarrollo* de SI como para el subproceso de *Diseño* del SI.
- **ISO/IEC/IEEE 12207** (ciclo de vida del software), **ISO/IEC 25010** (calidad del producto: adecuación funcional, eficiencia de desempeño, compatibilidad, **usabilidad**, fiabilidad, **seguridad**, **mantenibilidad** y **portabilidad**), **CMMI** (cinco niveles de madurez: Inicial, Gestionado, Definido, Gestionado cuantitativamente y En optimización), ISO 9001, ITIL, COBIT, PMBOK, PRINCE2.

## Pruebas del software

- **Verificación** («¿estamos construyendo bien el producto?») frente a **validación** («¿estamos construyendo el producto correcto?»). **Prueba**: ejecución para encontrar defectos; **depuración**: localizar y corregir su causa.
- **Niveles**: **unitarias** (componente aislado; JUnit, NUnit, pytest; *mocks* y *stubs*), **de integración**, **de sistema**, **de aceptación** (UAT; alfa y beta).
- **Tipos**: funcionales y no funcionales (**rendimiento**: carga, estrés, volumen, resistencia; **seguridad**; usabilidad; compatibilidad), **de regresión** (tras un cambio, comprueba que no se rompe lo existente), **de humo (*smoke*)** (verificación básica de que el build funciona), exploratorias.
- **Técnicas**:
  - **Caja negra** (sin ver el código): **partición de equivalencia**, **análisis de valores límite**, tablas de decisión, transición de estados. Ejemplo: campo edad válido 18-65 → clases válida (18-65) e inválidas (<18, >65); valores límite a probar: 17, 18, 19, 64, 65, 66.
  - **Caja blanca** (conociendo el código): **cobertura de sentencias**, **de decisiones/ramas**, de condiciones y de caminos. **Complejidad ciclomática de McCabe** `V(G) = decisiones + 1` (o `E − N + 2P`): número de caminos independientes; p. ej., 2 `if` y 1 `while` → V(G) = 4.
  - **Caja gris**: combinación.
- **TDD** (*Test-Driven Development*): ciclo **Rojo-Verde-Refactorizar** (escribir una prueba que falla, hacerla pasar, mejorar el código). **BDD**: comportamiento en lenguaje natural con **Gherkin** (*Given-When-Then*; Cucumber).
- **Pirámide de pruebas**: muchas pruebas unitarias, menos de integración y pocas de extremo a extremo (E2E).
- **Automatización**: **Selenium** (web), **JMeter** (carga), **Postman** (API), **SonarQube** (calidad estática y cobertura), **linters**. **Defectos**: registro, priorización (severidad/prioridad), seguimiento hasta su cierre.
- **Calidad del código**: revisión por pares (*code review*), **refactorización** (mejorar la estructura sin cambiar el comportamiento), *code smells*, **deuda técnica**, estándares de codificación.
