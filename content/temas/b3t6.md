## Arquitectura cliente/servidor

- **Cliente/servidor**: modelo en el que un **cliente** solicita servicios y un **servidor** los presta, comunicándose por red mediante un protocolo. El servidor está a la escucha; el cliente inicia la comunicación. Pueden residir en la misma máquina o en distintas.
- **Comunicación por *sockets***: el servidor hace `socket → bind → listen → accept`; el cliente `socket → connect`. TCP (orientado a conexión) o UDP (sin conexión). Otras tecnologías: **RPC**, **RMI** (Java), **CORBA** (obsoleto), **gRPC**, colas de mensajes (MOM).
- **Cliente ligero (*thin*)**: casi toda la lógica en el servidor (navegador). **Cliente pesado (*fat/rich*)**: lógica y proceso en el cliente (aplicación de escritorio). **Cliente híbrido/SPA**.
- **Frente a P2P**: en *peer-to-peer* cada nodo es a la vez cliente y servidor.

### Arquitectura en capas

| Arquitectura | Estructura |
|---|---|
| **2 capas** | Cliente (presentación + lógica) ↔ servidor de datos. Simple, pero el cliente es pesado y acoplado a la BD |
| **3 capas** | **Presentación** ↔ **lógica de negocio** (servidor de aplicaciones) ↔ **datos** (SGBD). Separa responsabilidades, escala por capas |
| **n capas** | Capas adicionales (servicios, integración, caché, seguridad…) |

- **Ventajas del multicapa**: mantenimiento y evolución independientes, **reutilización**, **escalabilidad** (horizontal por capa), **seguridad** (la BD no se expone al cliente), reparto de carga. **Inconvenientes**: mayor complejidad, latencia, más puntos de fallo y de despliegue.
- **Distinción**: **capas** (*layers*, organización lógica) frente a **niveles** (*tiers*, despliegue físico).
- **Escalabilidad y disponibilidad**: **balanceadores de carga** (capa 4 por IP/puerto, capa 7 por contenido HTTP), ***reverse proxy***, **cachés**, **CDN**, replicación, *clustering*. Aplicaciones **sin estado (*stateless*)** escalan mejor porque cualquier nodo puede atender cualquier petición; el estado se guarda en el cliente (token) o en un almacén compartido.
- **Middleware**: software intermedio que facilita la comunicación entre aplicaciones distribuidas (RPC, ORB, MOM, ESB).
- **SOA** (arquitectura orientada a servicios): funcionalidades expuestas como servicios interoperables y débilmente acoplados; **ESB** (bus de servicios empresariales). **Microservicios**: servicios pequeños, autónomos, desplegables de forma independiente, con **API Gateway**, frente al **monolito**.

## Servicios web

- **Servicio web**: componente software accesible por red mediante estándares abiertos (HTTP, XML, JSON) con interfaz procesable por máquinas (definición del W3C: interacción interoperable máquina a máquina).

### SOAP y servicios web «clásicos» (WS-*)

- **SOAP** (*Simple Object Access Protocol*): protocolo basado en **XML** para intercambiar mensajes estructurados. Mensaje: **Envelope** (obligatorio) con **Header** (opcional: seguridad, direccionamiento) y **Body** (obligatorio), y **Fault** para errores. Normalmente sobre **HTTP** (también SMTP). Admite estilos *document* y *RPC*.
- **WSDL** (*Web Services Description Language*): documento XML que describe el servicio: `types`, `message`, `portType`/`interface` (operaciones), `binding` (protocolo y formato) y `service`/`port` (dirección). Permite generar clientes automáticamente.
- **UDDI**: directorio para publicar y descubrir servicios (en desuso).
- **WS-\***: **WS-Security** (firma y cifrado XML, tokens), WS-Addressing, WS-ReliableMessaging, WS-Policy, WS-Transaction. Se usa en entornos corporativos y administrativos que exigen **seguridad a nivel de mensaje** y contratos formales.

### REST

- **REST** (*Representational State Transfer*, **Roy Fielding, 2000**): estilo arquitectónico, no protocolo. Restricciones: **cliente-servidor**, **sin estado**, **cacheable**, **interfaz uniforme**, **sistema en capas** y **código bajo demanda** (opcional).
- **Interfaz uniforme**: identificación de recursos mediante **URI**, manipulación mediante **representaciones** (JSON, XML), mensajes autodescriptivos y **HATEOAS** (los enlaces guían al cliente).
- **Métodos HTTP**:

| Método | Uso | Seguro | Idempotente |
|---|---|---|---|
| **GET** | Consultar un recurso | Sí | Sí |
| **POST** | Crear / acción no idempotente | No | **No** |
| **PUT** | Reemplazar o crear en una URI conocida | No | Sí |
| **PATCH** | Modificación parcial | No | No (en general) |
| **DELETE** | Eliminar | No | Sí |
| **HEAD / OPTIONS** | Cabeceras / métodos permitidos | Sí | Sí |

- **Códigos de estado HTTP**: **200** OK, **201** Created, **204** No Content, **301/302** redirecciones, **304** Not Modified, **400** Bad Request, **401** Unauthorized (falta autenticación), **403** Forbidden (autenticado, sin permiso), **404** Not Found, **405** Method Not Allowed, **409** Conflict, **415** Unsupported Media Type, **429** Too Many Requests, **500** Internal Server Error, **502** Bad Gateway, **503** Service Unavailable, **504** Gateway Timeout.
- **Modelo de madurez de Richardson**: nivel 0 (un endpoint), 1 (recursos), 2 (verbos HTTP y códigos), 3 (**HATEOAS**).
- **Descripción de APIs**: **OpenAPI** (Swagger). Buenas prácticas: sustantivos en plural (`/expedientes/123`), versionado (`/v1/…`), paginación, filtrado, errores homogéneos.

### Otras tecnologías

- **GraphQL**: lenguaje de consulta para APIs con un **único endpoint**; el cliente indica qué campos necesita (evita *over/under-fetching*).
- **gRPC**: RPC de alto rendimiento sobre **HTTP/2** con **Protocol Buffers**; admite *streaming*.
- **WebSocket** (RFC 6455): canal **bidireccional full-duplex** persistente sobre TCP (`ws://`, `wss://`). **Server-Sent Events** (flujo unidireccional servidor → cliente). **Webhooks**: llamadas HTTP de retorno ante eventos.
- **Mensajería asíncrona**: colas y *brokers* (**RabbitMQ**/AMQP, **Kafka**, **MQTT** para IoT).

| Aspecto | SOAP | REST |
|---|---|---|
| Naturaleza | Protocolo | Estilo arquitectónico |
| Formato | Solo XML | JSON, XML, texto… |
| Contrato | WSDL (estricto) | OpenAPI (opcional) |
| Transporte | HTTP, SMTP… | HTTP |
| Estado | Admite operaciones con estado | Sin estado |
| Seguridad | WS-Security | TLS + OAuth 2.0 / JWT |

## Seguridad de servicios web

- **TLS** para el transporte; **WS-Security** en SOAP; en REST: **API keys**, **HTTP Basic** (solo sobre TLS), **OAuth 2.0** (autorización delegada: *authorization code* con **PKCE**, *client credentials*), **OpenID Connect** (autenticación sobre OAuth 2.0) y **JWT** (*JSON Web Token*: `cabecera.carga.firma`, codificado en Base64URL; firmado, no necesariamente cifrado). **mTLS** entre servicios.
- **Defensa**: validación de entradas, *rate limiting*, API Gateway, mínimos privilegios, registro y auditoría; referencia **OWASP API Security Top 10**.
- **Identidad federada**: **SAML 2.0** (XML; SSO corporativo; usado por Cl@ve) frente a OAuth/OIDC (JSON).

## Servicios web en la Administración

- La **intermediación de datos** de la AGE (PID) utiliza servicios web **SOAP** con mensajes firmados, bajo el esquema **SCSP** (*Sustitución de Certificados en Soporte Papel*). La NTI de **Protocolos de intermediación de datos** y el **ENI** buscan la interoperabilidad entre Administraciones. Otros servicios con interfaz de servicio web: **FACe** (facturas), **@firma** (validación de firmas) y **Cl@ve** (SAML 2.0).
